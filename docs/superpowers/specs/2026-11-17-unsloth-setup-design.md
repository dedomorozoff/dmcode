# Unsloth в /setup: ключ не теряется, URL известен, модель выбирается из списка

Дата: 2026-11-17. Малая правка (три точки, два пакета).

## Зачем

Живой прогон Unsloth через `/setup` показал три проблемы:

1. **Ключ вводится дважды** — баг. В TUI-визарде путь «опция с ключом, но без
   URL» (Unsloth, свой endpoint) цепочкой ключ → URL → модель, и ключ живёт
   только в буфере ввода: при переходе к URL буфер очищается, на стадии модели
   заполняется текстом модели, и `applySetup` отправляет **имя модели** как
   ключ. Probe отвечает 401, `handleSetupCheck` возвращает на стадию ключа,
   второй ввод (уже с ключом в буфере) проходит.
2. **URL спрашивается, хотя он документирован.** Unsloth Studio — локальный
   сервер с фиксированным endpoint'ом по умолчанию `http://localhost:8888/v1`
   (доки Unsloth: `unsloth studio -H 0.0.0.0 -p 8888`). Ollama таким же образом
   уже вписана (`127.0.0.1:11434/v1` в строке пресеты).
3. **Модель спрашивается текстом, хотя dmcode умеет `/models`.** Каталог Unsloth
   — что пользователь скачал, то и есть; заранее его не знает никто. Но
   `config.ListModels` уже есть и уже вызывается probe'ом ключа в `applySetup`.

## Выбранный подход (A)

Три точные правки:

1. **Ключ — в поле, не в буфере.** `m.setup.key` заполняется на стадии ключа,
   `applySetup`/`SetupVars` читают его. Баг двойного ввода исчезает у обеих
   затронутых строк (Unsloth, свой endpoint); probe снова честный.
2. **Unsloth-строке вписан URL** `http://localhost:8888/v1` (как Ollama);
   стадия URL для неё исчезает. Порт меняли — остаётся строка «свой endpoint».
   Заодно `EnvKey` меняется с `OPENAI_API_KEY` на `UNSLOTH_API_KEY`: так ключ
   называется в доках самого Unsloth (`os.environ["UNSLOTH_API_KEY"]`), и
   настройка Unsloth перестаёт перезаписывать рабочий `OPENAI_API_KEY` от
   OpenRouter/своего endpoint'а (это моё решение, не запрос — причина: то же
   правило, по которому keyless-строки не трогают чужие переменные).
3. **Модель — из списка endpoint'а.** Probe в `applySetup` уже зовёт
   `ListModels`: если у опции модель не задана и список получен — показать
   пикер (стрелки + enter, как список провайдеров) и коммитить выбранный id
   без второй пробы. Список не получен (сервер выключен, endpoint не умеет
   `/models`) — текстовый промпт как сейчас. То же в stdin-визарде
   (нумерованный выбор), чтобы визарды не разъехались.

## Отвергнутые варианты

- **B (только баг + URL, модель текстом)** — оставляет жалобу «мы не знаем,
  какая модель есть».
- **C (пикер для любого провайдера)** — у всех остальных опций модель задана
  в пресете и проверена живым аудитом; пикер там лишний ход.
- **Автодетект `UNSLOTH_API_KEY` на старте** (`keyedPresets`) — отложен: у
  Unsloth нет дефолтного id модели, а выдуманный id роняет провайдера целиком
  (урок аудита провайдеров). Автодетект без модели — отдельная работа.

## Инварианты, которые меняются

- `TestSetupOptionsAreWellFormed` запрещал «URL есть, модели нет» — правило
  старого визарда («промпт только когда URL пуст»). Новое правило: визард
  спрашивает всё, чего не хватает; опция с URL и без модели обязана уметь
  `/models`. В конфиг-тесте строка Unsloth разрешается явно, стадийная
  машина (что строка доходит до выбора модели) проверяется в `internal/ui`.
- `TestUnslothAsksForURLAndModelInTheWizard` фиксировал нынешнее поведение
  (URL-стадия для Unsloth) — заменяется тестом нового пути: ключ → пикер
  моделей из probe → коммит; и тестом, что ключ доживает до `SetupVars`.

## Чего не делать

- Не трогать остальных провайдеров, их модели и `keyedPresets`.
- Не добавлять вторую пробу ключа после выбора модели — список уже получен
  тем же запросом, которым пробуют ключ.
- Не делать пикер модельным диалогом поверх всего интерфейса — он живёт
  внутри `/setup`, в его собственных стадиях.
