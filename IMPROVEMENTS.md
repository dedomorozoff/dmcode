# План улучшений dmcode

> Составлен 2026-11-05 по текущему дереву (v0.2.5, `main` @ `3e601fb`).
> Проверено перед написанием: `go vet ./...` — чисто, `go build` — ОК,
> 150 тестовых файлов против 107 исходников, CI (linux/macos/windows + `-race` + golangci-lint) настроен.
>
> Это **не** дубль `ROADMAP.md`: там — что уже сделано и что открыто как фича.
> Здесь — анализ состояния и приоритетный порядок работ, с честной оценкой
> «что важнее». Пункты, уже отмеченные в ROADMAP как открытые, помечены ссылкой на него.

---

## 1. Анализ: силу и слабости

### Что уже хорошо и ломать не надо

- **Архитектура**: чистое деление на `internal/*`, зависимости идут в правильную
  сторону (`ask` как шов между `tools` и `ui`, `pathnorm` как единый ответ про пути).
- **Безопасность файлов**: атомарные записи, граница workspace с перепроверкой
  после симлинков, turn-журнал для undo — всё с тестами.
- **Дисциплина тестов**: `e2e_test.go` на настоящем проводе, регрессии на
  конкретные сломанные payload'ы, guard-тесты на классы («каждый инструмент
  описан», «клипборд-тесты не трогают настоящий клипборд»).
- **Документация решений**: AGENTS.md объясняет *почему*, а не только *что* —
  это редкость и актив.

### Главные риски (то, из чего вырос приоритет)

1. **Ядро проверено только тестами.** Сам проект честно перечисляет в AGENTS.md
   два десятка пунктов «unit-покрыто, живой сессией не проверялось»: rewind,
   round-trip сессий, ask-оверлей, `switch_mode`, субагент, цитаты, картинки до
   vision-endpoint, `/compact`, yolo. Это не баг — это **неизвестное**: каждый
   пункт может оказаться рабочим, а может сломаться в первый же живой вечер.
2. **Отмена не убивает дерево процессов.** `run_command` использует
   `exec.CommandContext` (`internal/tools/tools.go:1303`), который на Windows
   убивает только оболочку, а не её детей; на Unix нет process group. Долгий
   `go test`/сборка переживает `Esc` и держит CPU.
3. **`internal/ui/ui.go` — 6821 строк.** Пакет уже разрезан по файлам
   (jump, cite, ask_view, …), но `ui.go` остаётся точкой, где любая правка TUI
   конфликтует с любой другой. Это тормозит и людей, и агентов, правящих код.
   *Закрыто в C1: `render.go` и `frame.go`, механически, 6821 → 5960.*
4. **Картинки — половина функции.** Чтение клипборда было только на Windows
   (закрыто в D2: Linux/macOS — лесенка `wl-paste`/`xclip`/`osascript`), WebP
   объявлен в списке расширений, но декодера в сборке нет.
5. **Мелкие дыры согласованности**, задокументированные как сознательные:
   rewind не переписывал `~/.dmcode/history.jsonl` — закрыто в B3 (отменённый
   промпт теперь вычёркивается и с диска).

## 2. План работ

### Фаза A — Живая верификация ядра (самый высокий приоритет)

*Цель: превратить «проверено тестами» в «проверено». Ни один новый пункт не
начинать, пока A не закрыт — иначе неизвестное копится.*

- [x] **A1. Чек-лист живых прогонов** — перенесён в `VERIFICATION.md`,
      сценарии ниже живут там;
      ровно из «Known gaps» AGENTS.md, каждый с шагами: что напечатать, что
      должно случиться, что делать если нет. Сценарии:
  - [ ] A1.1 `ctrl+z` против живой сессии с тул-ходами: проверить, что память
        модели тоже порезалась (спросить «что ты только что делал?»);
  - [ ] A1.2 перезапуск с `-s`: сверить восстановленный транскрипт с записанным;
  - [ ] A1.3 `ask_user` + таймер `DMCODE_ASK_TIMEOUT` в живом ходе;
  - [ ] A1.4 `switch_mode` plan→act: runner пересобран, ход не подвешен;
  - [ ] A1.5 `sub_agent`: отчёт влезает в окно родителя, обрезан при переполнении;
  - [ ] A1.6 картинка → живой vision-endpoint (OpenRouter/Gemini-класс):
        `image_url` data URL принимается, модель отвечает про картинку;
  - [ ] A1.7 клик по цитате `path:line` в живом терминале;
  - [ ] A1.8 `/compact` в живом TUI-ходе;
  - [ ] A1.9 yolo-ход целиком (shift+tab → агент действует без вопросов);
  - [ ] A1.10 `read_file` paging: модель сама листает большой файл через
        `next_offset` без подсказки;
  - [ ] A1.11 откат файлов: живая сессия, `write_file`/`move_file`, затем `ctrl+z` —
        файлы на месте, панель CHANGES не врёт;
  - [ ] A1.12 GIF-превью и картинки в редакторе на живом терминале (iTerm2,
        Windows Terminal, gnome-terminal).
- [ ] **A2. Прогнать A1 и завести баги.** Каждый провал — отдельный коммит с
      фиксом и тестом; каждый успех — галочка в чек-листе и вычёркивание из
      «unverified» в AGENTS.md.

*Критерий готовности: AGENTS.md больше не содержит список «still unverified».*

### Фаза B — Отмена и процессы

- [x] **B1. Убийство дерева процессов** (`run_command` и фоновые команды).
      На Unix — `Setpgid` + `syscall.Kill(-pgid, …)`; на Windows — job object с
      `KILL_ON_JOB_CLOSE`, потому что Git Bash/Cygwin пересаживают детей на
      другого родителя и `taskkill /T` внуков просто не видит. Тесты
      (`kill_tree_*_test.go`): спящий дочерний процесс умирает вместе с
      оболочкой, засчитывается только <4 с после отмены — иначе это спасал
      пятисекундный `WaitDelay`, а не дерево.
      *Остаток:* PTY редактора (`ptyterm`) этим сеймом не покрыт — пункт B4.
- [x] **B2. Отмена субагента.** Оказалось проверено, а не починено: отмена уже
      доходит — модельный запрос субагента уходит на контексте родителя
      (`http.NewRequestWithContext`), и прерыванный ход обрывает живой стрим.
      Утверждение «доработает свой такт» было устаревшим; теперь это закреплено
      тестом `internal/agent/subagent_cancel_e2e_test.go`, а не словами.
      *Остаток переехал в B4: редакторный PTY.*
- [x] **B3. `history.jsonl` и rewind.** Вычёркивать, не документовать:
      `removeLastPromptHistory` стирает последнюю строку файла (temp+rename),
      но только если она совпадает с отменённым промптом — вторая сессия dmcode,
      дописавшая свой промпт в общий файл, его не теряет. Память и диск теперь
      говорят об одном и том же промпте; тесты — `history_test.go`
      (`TestRemoveLastPromptHistoryErasesOnlyItsOwnPrompt`,
      `TestRewindTakesThePromptOffDisk`).
- [x] **B4. Редакторный PTY и дерево процессов.** Сейм вынесен в
      `internal/proctree` (группа процессов на Unix, job object на Windows) и
      общий с `run_command`; `ptyterm.Close` теперь валит всё дерево, а не
      только шелл. Тест `ptyterm_tree_windows_test.go` меряет то же, что и
      `kill_tree`: фонущий `sleep` должен исчезнуть в пределах нескольких
      секунд после `Close`.

### Фаза C — Разрезание `internal/ui/ui.go`

*Цель: ни один файл не был монолитом; правка оверлея не задевает рендер.*

- [x] **C1.** Вынесено механически: `render.go` — блок рендера строк
      (`transcriptRow`/`rowStyle`/`renderedRows`/`rowRows`/`diffRows`/
      `renderHistory`/перенос по ячейкам), плюс `cachedLine` и текст-форматеры
      `toolLine`/`toolArgs`/`truncate`; `frame.go` — геометрия кадра
      (`sidebarVisible`…`layout`) и сборка (`modalUp`/`chatOverlayUp`/
      `buildFrame`/`paintSelection`). `ui.go`: 6821 → 5960. Перенос проверен
      мультимножеством строк: ни одной потерянной строки, добавлены только
      package/import-заголовки. Диспатчер команд не тронут.
- [x] **C2.** Не сделан по условию плана: перенос не показал, что
      `Update`/`View` неподъёмны — гигантских switch'ей после C1 механически
      не разрезать было бы честнее таблицей, но ни один перенос этого не
      потребовал. *Зато обнажился третий кластер (~560 строк оверлейных
      коробок: `suggestBox`, `listView`, `panelBox`, `paletteBox`, …), который
      по конвенции просит `dialogs.go` — это отдельная правка, не C1/C2.*

### Фаза D — Картинки: закрыть функцию

- [x] **D1. WebP- и BMP-декодеры**: `golang.org/x/image/webp` + `x/image/bmp`
      пустым `_ import` в `imgprev` (проект уже на `x/image`). Убрало
      «расширение есть — декодера нет» и в чате, и в редакторе; тесты проверяют
      и присоединение картинки в UI, и то, что на wire уходят те же байты.
- [x] **D2. Картинка из клипборда на Linux/macOS:** лесенка инструментов в
      `clipimg_cmd.go` — Linux: `wl-paste --type image/png`, затем `xclip
      -selection clipboard -t image/png -o`; macOS: `osascript`, пишущий PNG
      в фиксированный temp-файл (путь выбирает эта сторона, никогда — stdout).
      Правило «первый *раскодируемый* ответ», урок `firstImage`, перенесено
      целиком; отсутствие инструмента — не ошибка, а «нет картинки», и ctrl+v
      по-прежнему вставляет текст. Регистрация декодеров вынесена в
      `internal/imagedec`, чтобы список был один. Тесты — через подменённые
      `runCommand`/`commandExists`, реальный клипборд не трогают. *Живым
      Wayland/X11/pasteboard проверки не было — machine not present, см.
      преамбулу AGENTS.md.*
- [ ] **D3.** После A1.6 (живой vision-endpoint) — снимает ограничение
      chat-wire в коде там, где ADK наконец примет InlineData, либо фиксирует
      отказ как поддержку `DMCODE_API=chat`-only со ссылкой на SDK-баг.

## 3. Чего делать НЕ надо (зафиксировать решение)

- **SQLite-хранилище** — пока нет доказательств, что JSONL упёрся; замена
  проверенного формата на непроверенный = регрессия ради гипотетической нужды.
- **Встраивание AGENTS.md в системный промпт** — решение «агент читает файл
  сам, а не получает преамбулу» принято и обосновано в ROADMAP фаза 5.3; не
  откатывать без новой причины.
- **Глобальное переписывание TUI на другую библиотеку** — render-кэш,
  построчный кэш и hit-testing кликов завязаны на текущую lipgloss-арифметику;
  переезд обнулил бы именно те тесты, которые сторожат регрессии.
- **Отключение мыши по умолчанию** — `/mouse` уже даёт выход; обратное
  решение (по AGENTS.md, «нативное выделение потеряно, пока мыша включена»)
  принято осознанно.

## 4. Порядок и зависимости

```
A (живая верификация) ──┬──> B (отмена/процессы: чинится по багам из A1)
                        ├──> D3 (vision-endpoint ответ A1.6)
                        └──> далее C, E, F — независимы, но E/F только после A
```

- **A первее всего**: он определяет, что из «проверено тестами» вообще нужно
  чинить, и он же единственный пункт, который нельзя ускорить параллельными
  агентами — живой терминал один.
- **C можно дробить**: перенос кода в новые файлы не зависит от A и B и почти
  не конфликтует с ними (движение одностороннее: после C багофиксы A ложатся
  в мелкие файлы вместо одного огромного).
- **E и F — только после A и B**: строить новые UX поверх ядра, которого никто
  не видел живьём, значит строить на неизвестном.

Ориентировочная ёмкость: A ≈ 1–2 вечера ручной работы + фиксы;
B ≈ 1 день на платформенную часть; C ≈ день механики; D ≈ 2–3 дня;
E — по пунктам независимо; F1/F2 ≈ день каждый.
